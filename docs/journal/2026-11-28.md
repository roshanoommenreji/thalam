# 2026-11-28

### THL-32: the graph queries (SPEC-002 Task 5, R9, R10, R11)

**Built:** `thalam_shared.graph`, pure functions over one frozen snapshot of the release graph.
There is no database and no model. Task 7 builds the same Graph from the fixture files and Task 10
builds it from Postgres, and these functions answer both (R8).
- **`upstream` and `downstream`:** transitive over the catalogue's declared dependencies.
  `downstream` is a component's blast radius.
- **`prod_version`:** the highest version whose current state is `released`. Rolled-back and
  cancelled releases never count.
- **`must_ship_before(c, v)`:** each need is handled in one of three ways:
  - prod already satisfies it;
  - the lowest in-flight release that satisfies it becomes a step, and that release's own needs
    are followed;
  - nothing can satisfy it, so it is a blocker.
  Steps come upstream first.
- **`release_order()`:** every in-flight release, each after the releases it needs.
- **Loops:** a loop in the needs is an error that names it.

**The code review found:**
- **The loop error read backwards.** graphlib reports a cycle as a list in which each node comes
  before the next. Here, coming before means being needed, so `a → c → b → a` meant "a is needed by
  c". The fixed message:
  - follows "needs";
  - starts from the smallest label, so one loop always prints the same way;
  - leaves out releases that only lead into the loop.
- **Two graphs from the same facts could compare unequal.** Needs were sorted by component only, so
  two ranges on one component, given in the other order, made a different Graph. Tasks 7 and 10
  prove the load by comparing a file-built Graph with a Postgres-built one, so that check would
  have failed for no real reason. Needs and windows now sort on every field.
- **Ties sorted versions as text**, so `x 1.10.0` came before `x 1.9.0`. Ties now go by component,
  then lowest version first.
- **The cancelled-release test proved nothing.** Its cancelled release was higher than the one
  chosen, so it lost anyway. In the new test, the cancelled and rolled-back releases are the
  lowest, and the test fails when the in-flight filter is removed. Every in-flight state is now
  tested as a step.
- **Smaller fixes:**
  - `make_graph` refuses a malformed graph:
    - an unknown component in an edge, a release or a need;
    - a component that depends on itself;
    - a version or range that does not parse;
    - the same release listed twice.
    Versions are normalised, so `1.0` becomes `1.0.0`.
  - A version range takes plain `X.Y.Z` only. Epochs, pre-releases, local versions and empty parts
    are refused; an epoch such as `>=1!2.0` had silently blocked every need.
  - Version parsing uses `[0-9]` and ASCII spaces only. `\d` also matches other scripts' digits,
    so `٢.٣` had been read as `2.3.0`.
  - A blocker's reason names the range and what prod runs, for example
    `no release satisfies <2 (prod runs 3.0.0)`.
  - New tests: a diamond, where a shared upstream release appears once; and an unknown component
    in a need.

**The plan was wrong in four places:** its code had the unequal sort, the text tie-break and the
backwards loop message, and its cancelled-release test was the weak one. Two follow-ups:
- Task 9's blocker test quotes the old reason text, so it changes when Task 9 starts.
- SPEC-002-R10 says the loop error names every *component*. It names releases, which is more
  precise, so the spec's wording changes at Task 12.

**Open:**
- **For Roshan (SPEC-002-R11):** nothing orders two in-flight versions of one component, except a
  need between them.
  - Within a step, the lower version goes first.
  - Across steps, a hotfix `1.9.1` that needs something still in flight is listed after a `1.10.0`
    that does not.
  A "lower version ships first" rule would close the gap, but it changes what R11 says.
- When there are several loops, the error names one.
- A step records only the first release that needed it.

**Construction note:** the first code reviewer hung overnight with an empty log, most likely
because the laptop slept. It was stopped after 12 hours, and a fresh reviewer finished in 2
minutes.

**Measured:** about 1 hour of agent time across two sessions, not counting the hung reviewer.
Defects: 4 important and 8 minor, all fixed before merge. Tests: 381 (329 + 52). Subagent tokens:
about 0.6 M (implementer, spec review, code review, two rounds of fixes, and the re-review).

### THL-33: the Backstage catalog reader (SPEC-002 Task 6, R4)

**Built:** `thalam_collector.catalog` and `thalam_collector.problems`, the first reader of the
company folder.
- **What it reads:** every `catalog/*.yaml`, with `yaml.safe_load_all`, so a planted tag never
  builds a Python object.
- **Groups and Components:** each Component's owner must be a Group in the catalog, and each
  `dependsOn` must name a Component in the catalog. Other kinds (API, System, Resource) are skipped.
- **Problems:** what is wrong comes back as a list of Problems, each naming its file and field.
  Task 8 refuses a load that has any (R6).
- **Untrusted text:** descriptions are flattened and capped at 1,000 characters, and any value
  from a file is shown only through `repr()`.

**Both reviews:** the plan's code passed its own 9 tests. The implementer flagged six likely bugs
anyway, and the spec and code reviews confirmed them and found more. All are fixed before merge.
- **Some files crashed the reader instead of naming themselves.** These went past the YAML-only
  `except`:
  - invalid UTF-8;
  - a folder named `x.yaml`;
  - a bad date such as `description: 2024-13-45`, which PyYAML raises as a bare `ValueError`;
  - 20,000 nested brackets.
  Each is now a problem at `(file)`. A file over 1 MiB is refused before it is parsed, because
  pure-Python PyYAML took 83 s on 4 MB. The re-review then found `a: !!timestamp zzz`, which
  raises `AttributeError` from inside PyYAML: a hand-tagged scalar can raise anything. So the
  reader now ends with a catch-all that reports only the exception's class.
  - **Shared:** the hardened reader is now `thalam_collector.files.read_yaml`, so Task 7's
    manifests and calendar can use it instead of a second copy.
- **A typo could delete a component.** A document with no `kind`, or `kind: component` in lower
  case, matched no branch and vanished silently. Task 8's mirror retires every component missing
  from the catalog, so one typo would have retired a live component. In the same way, an empty
  catalog read as "no components", which would have retired them all. Both are now problems.
- **NUL in a description would have broken Task 8.** Postgres TEXT refuses NUL, and a lone
  surrogate cannot be encoded, so the load would have failed after a clean read. Descriptions are
  now flattened, not just capped: control characters, line separators and whitespace runs become
  one space (CLAUDE.md rule 4).
- **The YAML error printed the wrong line.** It showed PyYAML's context ("while scanning for the
  next token") and dropped the problem itself. It now gives the problem and its line number.
- **Names are now compared ignoring case,** as Backstage compares them, so `api` and `API` are one
  name defined twice. A `dependsOn` or `owner` written in another case still resolves, and keeps
  the target's own spelling.
- **Every later duplicate is named,** each at its own file and field. That covers Groups too, which
  a set had hidden.
- **Smaller fixes:**
  - the name pattern no longer accepts a trailing newline;
  - length limits on `type`, `lifecycle`, `owner` and `dependsOn`;
  - a namespace other than `default` is a problem;
  - a `.yml` file is a problem, not silently ignored;
  - files are read in name order, so "first defined at" is the same on Windows and Linux.

**The plan was wrong** in all the places above. Its test that other kinds are skipped had to gain
a component, because an empty catalog is now a problem.

**Open:**
- SPEC-002-R4 says "`catalog-info.yaml` files", but the reader takes every `catalog/*.yaml`. Align
  the wording at Task 12.
- Subfolders of `catalog/` are not read.
- A `dependsOn` written without `component:` is refused. That is stricter than Backstage, which
  assumes Component, but it fails closed.
- Task 7 must keep the rule this reader relies on: never walk, copy or print a whole raw document.
  Aliases are shared objects, so a "billion laughs" file stays cheap only while nothing walks it.

**Measured:** about 1.5 hours of agent time. The first code review alone took 42 minutes.
Defects: 8 important and 9 minor, all fixed before merge. Tests: 414 (381 + 33). Subagent tokens:
about 0.7 M (implementer, spec review, code review, three rounds of fixes and two re-reviews).

### THL-34: release manifests, Jira files and the calendar (SPEC-002 Task 7, R5, R6)

**Built:** `thalam_collector.company`, which reads the rest of the company folder and checks all of it.
- **Manifests:** each `releases/*.yaml` gives a component's versions, its needs (an upstream
  component and a version range) and its events. Unknown fields are refused.
- **Life cycle:** every event is checked as it is read.
  - It must be later than the one before.
  - It must be a legal move.
  - A replan is only allowed while the release is in flight.
  - Its time must carry a UTC offset.
- **Jira-shaped files:** `versions.json` and `search.json` give each release its Jira version id and
  its items. Fields Thalam does not read are ignored, and summaries are capped at 255.
- **Calendar:** `calendar.yaml` holds the freeze and blackout windows.
- **Every problem is collected,** each with its file and field, and a load with any problem writes
  nothing (R6). A need on a component outside the catalog's `dependsOn` loads with a warning.
- **`to_graph`** builds the same Graph that Task 10 will read back from Postgres.

**The spec review found two gaps in the plan's code:**
- **The plan's file reader repeated the gaps Task 6 had just closed.** A date such as
  `starts: 2026-13-19`, a file that is not UTF-8, or deep nesting crashed the load without naming a
  file. The YAML files now use the shared `files.read_yaml`, and the Jira files use a new
  `files.read_json` with the same limits.
- **A Jira issue listed twice reached the database.** `release_item` is unique on
  `(release, jira_key)`, so Task 8 would have failed with an `IntegrityError`, not a message naming
  the file. It is now a problem.
- **Smaller fixes:** a missing or empty `releases/` folder and a `.yml` manifest are problems; an
  empty file, or one with two documents, is a problem; a name that matches a catalog name apart from
  case gets "did you mean"; one cause no longer prints a cascade of follow-on problems. Where a
  cause hides a whole class of checks (the catalog's problems hide the manifests' name checks, and
  `versions.json`'s hide the issues' version ids), one summary problem says so, so nobody is
  surprised by a second batch after fixing the first. A quoted date gets a hint to write it
  unquoted.

**The code review found six important problems and some smaller ones, all fixed before merge:**
- **A hostile key name reached the terminal.** `needs: {"<ESC>[2J...": ...}` put the escape
  sequence into the printed field name. Field names are now flattened.
- **Window names and Jira ids were stored raw.** A NUL would have failed in Postgres after a clean
  read. Window names are flattened, and Jira ids must be numeric, as Jira's are.
- **A range with 4,400 digits loaded, then crashed the queries** (Python limits integer text to
  4,300 digits). `graph.py` now takes at most nine digits per number.
- **Invisible characters survived flattening.** 154 characters of Unicode category Cf passed,
  including zero-width characters and the Tag block (U+E0000 to U+E007F), which can carry hidden
  instructions. Jira summaries are read by a model later, so they now collapse to a space. One
  exception is spelling: a single zero-width joiner or non-joiner after a letter stays, because a
  Malayalam chillu letter (na, virama, joiner) and many Persian words need it. The re-review caught that the first
  version split them. A run of two or more joiners is still flattened, since hidden data can be
  written as a run. A lone joiner can still carry one bit, which is accepted: the Tag block is
  what models read as text.
- **A repeated key took the last value silently.** `needs: {db-svc: ">=2", db-svc: ">=9"}` loaded
  with `>=9`. It is now a problem, in YAML and in JSON.
- **The parser was slow.** Reading a legal company of 500 manifests took 33 s with pure-Python
  PyYAML. It now uses libyaml when it is installed (still a safe loader), which brings it to 9 s.
  The two parsers word errors differently, so no test depends on the wording.
- **The life-cycle rules had no tests yet:** the plan leaves them to Task 8, which skips without a
  database. A 26-row table in `test_releases.py` covers them now.
- **Smaller fixes:** years outside 2000 to 2100 and integers or strings where a date belongs are
  problems; a first event that is not `planned` says so; no production `assert`; `str(exc)` is
  never used; and no test source holds a literal invisible character.

**The plan was wrong** in its file reader, its Jira duplicate check, its text handling and its missing
life-cycle tests. Its `MINIMAL` fixture was fine.

**Open:**
- **`release.jira_version_id` is written once.** A Jira version created after a release was first
  loaded fails the load with a clear message. ADR-0015 already says Phase 3 must revisit it, because
  the executor creates Jira versions after a release is planned.
- **"Names no release" is strict:** every Jira version must match a manifest release. That is fine
  for a fixture, but a real Jira project has many old versions, so it needs a warning mode later.
- **Not checked yet:** Jira's `released` flag against the manifest, and a truncated `search.json`
  (`total` above the issues listed). Both belong in `Company.warnings`.
- **A file over 1 MiB is refused,** which a `search.json` of about 10,000 issues would exceed.
- **Task 8's command should print at most the first 50 problems.** A 360 KB manifest of bad
  releases gave 14,005.

**Measured:** about 1 hour of agent time, with a pause when the 5-hour limit ran out. The first fix
round hit it and resumed without losing work. Defects: 8 important and about 14 minor, all fixed
before merge. Tests: 567 (414 + 153). Subagent tokens: about 1.4 M (implementer, spec review, code
review, three rounds of fixes and the re-reviews).
